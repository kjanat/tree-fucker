# Native coordination platform contracts

All platforms share the ownership protocol, the authority, and the snapshot journal. Each native adapter supplies four things: the scope identity, the retained storage, the nonblocking bookkeeping lock, and lifetime evidence for operation owners that includes the owner's incarnation. Each adapter must satisfy the same [acceptance histories](coordination.md#acceptance-histories).

## Current implementation and activation

| Target  | Current shared backend                                            | Current mode selection                             | Native activation gate                                                                                               |
| ------- | ----------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Linux   | Private tmpfs journal, pinned sibling anchor, `flock` owner slots | Opt-in shared coordination                         | Linux subprocess, namespace, recovery, and performance acceptance                                                    |
| Windows | Private NTFS/ReFS journal, pinned anchor, exclusive owner handles | Opt-in shared coordination                         | Native x64/ARM64 suites and all 22 guest session histories pass at `69d0f00`; reboot retains accounting              |
| macOS   | Root-qualified tmpfs journal and pinned anchor                    | Opt-in; physical sleep/wake remains unverified     | Native tmpfs, sandbox, root transition, inherited ownership and resource tests pass; physical transition remains #20 |
| FreeBSD | Root-qualified tmpfs journal and pinned anchor                    | Opt-in for compatible roots; capability rejection  | Retained tmpfs discovery, jail/capability identity, inherited owner locks                                            |
| illumos | Zone-qualified tmpfs journal and pinned anchor                    | Opt-in shared coordination                         | Native zone transitions, privilege restrictions, and resource acceptance                                             |
| Solaris | Unavailable                                                       | Required errors; Auto reports unsupported fallback | Verified lifetime mechanism and zone-local scope on the exact supported release                                      |

ProcessOnly is the default on every platform. `tests/coordination_policy.rs` tests mode selection, including the explicit outcomes on unsupported platforms. The CI matrix runs the portable tests on native Windows and macOS runners and on FreeBSD and OmniOS VMs. Those jobs run the process histories of each implemented adapter as part of its native release acceptance. The Solaris job cross-compiles to check API availability. Native Solaris execution is a separate gate.

No port may introduce a version-qualified rendezvous, reset retained debt after the final participant exits, or start a keeper process. Configurations and generations stay authoritative. A joining participant with stricter local limits still needs permission from both governors.

## Windows

Windows has per-session and global kernel-object namespaces. An ordinary client session needs `SeCreateGlobalPrivilege` to create a global file mapping, and Windows Store apps cannot use the global namespace. Discovery therefore cannot depend on creating a privileged global mapping. See [Kernel object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces).

The port contract has these requirements:

- The adapter must qualify the retained scope by the effective user SID. When the caller's session, logon identity, token identity, or token revision changes, the adapter must fence the captured connection. Those values must never select another scope name or budget. AppContainer callers are unavailable. The scope name must be deterministic and independent of the executable and the crate version. The adapter must apply a restrictive DACL to every coordination object and must validate existing objects before use.
- The accounting journal must live in verified host-local retained storage. A named mapping backed by the paging file is insufficient alone, because Windows can release its backing after all handles close. A mapping may cache a retained journal if the adapter checks the generation and object identity on reopening. See [Creating named shared memory](https://learn.microsoft.com/en-us/windows/win32/memory/creating-named-shared-memory).
- The adapter must acquire bookkeeping with a nonblocking `LockFileEx` byte-range lock on the pinned anchor. An independent open must conflict, even in the same process. The adapter must recover the journal after it acquires exclusion, including after the writer dies. Releasing the bookkeeping lock never proves that an operation owner exited. The lock byte lies outside the anchor header, and physical ownership uses separate exclusive file handles. See [Windows file locking](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex).
- The adapter must bind each participant to an identity-checked owner-slot file opened for read and write with no sharing. While it holds bookkeeping exclusion, reclamation must reopen the same file with conflicting data access, and the reopen must succeed. An attribute-only open is insufficient because sharing restrictions do not cover attribute access. Native tests must establish retention through duplicated and inherited handles. A failed open never proves that the owner exited. A newly started participant can recover after every earlier process exits, and it does not need cached process handles for them. See [CreateFile sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
- The adapter must select one common monotonic clock and bind its epoch to the retained scope identity. After a reboot or session recreation, the adapter must not read an older epoch as current elapsed time, and old and new authorities must not coexist.
- On a reboot, the adapter must keep the existing journal generation and debt. It must rebase the new boot's performance counter at the last logical timestamp the authority committed. The downtime and the time between that commit and the first reopen do not refill budgets. The adapter must publish the new epoch and the signed counter offset in the same recoverable journal as the accounting. Every later connection reuses this mapping, including after all handles close. Refill resumes as the new boot's counter advances. Transactions clamp individual readings to the committed authority time and leave the mapping unchanged.
- The adapter must reject remote or redirected storage, unsafe ACLs, conflicting object types, and unavailable sandbox access. It must never retry an unsafe scope under a new name.

Native tests must cover these cases: ordinary unprivileged discovery, independent sessions, duplicated and inherited handles, death of the bookkeeping thread while an I/O thread lives, complete process death, retained debt after every mapping closes, object replacement, and AppContainer denial.

`src/coordination/windows/handles.rs` implements the Windows file-handle operations. It keeps the complete 64-bit volume serial and the 128-bit file ID, rejects reparse points and hard links, and pins the expected owner file through the conflicting data-open probe. A missing or replaced file is an error. Only a successful exclusive reopen establishes final close. The returned handle holds exclusion through the caller's recovery commit.

`relative.rs` resolves an absolute drive root once, then opens each directory component against its pinned parent handle. Retained ancestors deny delete sharing. Child creation and owner recovery call `NtCreateFile` with a single relative component, synchronous handles, and reparse rejection. Neither reopening nor creation truncates existing accounting. The code rejects stream syntax, traversal, and ambiguous trailing characters before it opens anything. The authority can keep these parent pins and skip resolving its absolute path on every transaction. See [Relative object names and reparse rejection](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes).

`tests/coordination_windows.rs` tests duplicate retention, inherited ownership after the original process dies, slots that are missing, replaced, or hard-linked, closure of unrelated descriptors, and four kills of an actual journal writer. The last history keeps a separate operation owner alive and checks the retained journal accounting after all bookkeeping handles close. The complete suite passes natively in the Windows x64 and ARM64 CI matrix. `tests/coordination_cohorts.rs` adds the same held-read process cohorts and integrated owner-death histories that run on Unix. The independent-session and AppContainer histories passed in the disposable guest described below.

`coordination::windows::Scope` connects these file-handle operations to the shared journal and governor. Discovery calls `SHGetKnownFolderPath` with the effective user's token. The result is independent of environment variables and of executable, version, and session names. A retained sibling anchor binds the user SID, the boot-qualified clock, the parent directory, the state directory, the journal identity, and the generation. Only unpublished initialization may restart. The adapter reopens an existing committed account and checks it against the requested limits. Owner records keep the full 128-bit file ID, qualified by the root volume recorded in the anchor. Final-close recovery holds exclusive owner handles through the journal commit and can hand a reclaimed slot directly to the next participant.

Windows and Unix share the `Client`, preparation, physical-completion, and bounded deferred-settlement implementation in `client.rs`. On both, the same governor binding composes local and shared reservations. Native Windows fixtures cover generation and charge retention after every handle closes, owner-slot reuse, rejection of replacement and configuration changes, and actual Scan listing and lazy reads.

`security.rs` creates objects with a protected owner-only DACL and validates existing objects without changing their ACLs. A missing, null, inherited, broadened, or mismatched-owner descriptor is invalid state. The adapter does not report it as unavailable, because an unavailable result would permit Auto fallback. The effective thread token takes precedence over the process token. When impersonation or token modification changes the user SID, session, authentication identity, token identity, or token revision, the adapter fences the captured context. The authentication identity does not select the persistent scope name, so a new login cannot mint a fresh budget.

The test `low_integrity_and_restricted_callers_cannot_reset_a_retained_scope` runs native policy checks for a low-integrity impersonation token and for a token restricted to an Everyone SID. Both tokens try to open a retained authority that the original caller created. Access denial permits Auto fallback, and Required returns an error. When the test restores the original context, the exact journal, generation, and charge are intact. The test covers access-denied contexts and does not claim that every restricted token is unsupported. The adapter rejects AppContainer before it discovers or opens any state.

The disposable reboot guest contains real-session fixtures described in [native CI acceptance](../benchmarks/ci-acceptance.md). They cover ordinary-user discovery, two concurrent sessions of the same user, logoff and logon, another principal's storage, both UAC creation orders, a real AppContainer, and unsupported native storage. The fixture reports the actual token and session identities and succeeds only if every history passes. All 22 reported session histories and the real reboot passed on `69d0f009a25f8f78d09ee2453f12a6e60fcb7d9e` in [native acceptance run 41391215417](https://github.com/kjanat/tree-fucker/actions/runs/41391215417/job/125103138222). The retained report verifies distinct actual sessions and logons with one authority, final-close debt, one recovery surcharge, both UAC creation orders, rejection of another principal, the actual AppContainer identity, and unavailable outcomes before joining on FAT32, read-only NTFS, and mapped SMB. The native x64 and ARM64 suites also pass in [CI run 41391215416](https://github.com/kjanat/tree-fucker/actions/runs/41391215416). This completes the finite #18 evidence matrix. Physical Mac sleep and Solaris shared support remain separate exclusions.

The descriptor-policy and same-user impersonation tests pass under Wine 11.20. The file-based suite rejects Wine storage, because Wine's `server/file.c` rebuilds file security descriptors from Unix mode bits and drops the protected-DACL flag. The histories for file creation, reopening, and ACL mutation therefore need native Windows, and no weaker Wine permission path exists. See [Wine 11.20 source](https://dl.winehq.org/wine/source/11.x/wine-11.20.tar.xz).

`storage.rs` validates the opened file or directory before it accepts the ACL. A device-information query must succeed and identify a local disk or disk-filesystem device, and a failed query never establishes locality. The same handle must report writable NTFS or ReFS with persistent ACLs and file-ID support. At the drive root, capability validation runs before the full file-ID query. An unsupported volume therefore produces the documented unavailable outcome and never reaches the identity query. This check excludes remote devices even when their filesystem name and capabilities match a local one. See [Device information](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_file_fs_device_information) and [volume information by handle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew).

`clock.rs` reads the performance counter, converts it to integer nanoseconds, and keeps a retained epoch that holds the boot-entry GUID, the kernel boot sequence, and the counter frequency. The boot-entry GUID alone does not identify a startup. The code rejects malformed headers and incompatible frequencies and leaves accounting intact. The immutable anchor keeps the creation epoch. The journal stores the current epoch and the signed logical offset next to the retained budgets and ownership. A boot transition can leave the raw counter above or below the retained logical timestamp. Only that transition chooses an origin, and a reopen during the same boot reuses it. If the persisted mapping changes, the adapter fences an existing connection before it does any accounting. Counter readings from different threads can differ by one tick, so accounting clamps a reading to the committed time and leaves every connection's origin where it is. See [Performance counters](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps) and [kernel boot sequence](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-kuser_shared_data).

Counter-only snapshots keep format 2. Windows publishes its mapping in format 3. It migrates a retained format-2 snapshot under bookkeeping exclusion and keeps the generation, balances, and owners. Readers without format 3 support fail with an explicit error before admission. Byte-interruption tests cover the first publication and a second boot transition during journal-slot reuse, and each test leaves either the complete old authority or the complete new one. Native Windows fixtures cover simulated boot changes, independent connections, reopening after all handles close, and fencing on a stale mapping. The actual reboot fixture passed in [acceptance run 41372711016](https://github.com/kjanat/tree-fucker/actions/runs/41372711016/job/125046774864) on `6b996590e37f05c472ba37db6373e298ef772e18`. It runs as SYSTEM in session zero. That run does not cover ordinary-user logoff and logon or concurrent interactive sessions.

## macOS

Darwin `flock` supports nonblocking acquisition. Duplicated and fork-inherited descriptors refer to the same lock, and an explicit unlock through one reference releases it for all of them. The owner-slot design therefore must release lifetime locks only by closing, and bookkeeping uses an explicit scoped unlock. See [Apple's `flock(2)` manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html).

`coordination::macos::Scope` uses the shared Unix journal and pinned anchor on an administrator-mounted tmpfs at `/var/run/tree-fucker`. The adapter verifies the filesystem type, the private effective-user ownership, and the filesystem root identity. Native tmpfs is available through `mount_tmpfs` on macOS 11 and later. Its retained objects and the kernel monotonic clock share a boot lifetime. See [macOS `mount_tmpfs(8)`](https://man.freebsd.org/cgi/man.cgi?manpath=macOS+13.6.5&query=mount_tmpfs&sektion=8).

The adapter takes part in the same governor, diagnostics, independent-process tests, interrupted-publication tests, and Cargo benchmarks. A filesystem root that exposes incompatible retained authorities cannot fall back to a fresh local budget. An unknown domain identity stays participant-private under the common aggregate envelope.

The shared Unix backend reads `CLOCK_MONOTONIC` and never settles shared occupancy with Rust's process-local elapsed clock. Apple's [Libc clock implementation](https://github.com/apple-oss-distributions/Libc/blob/main/gen/clock_gettime.c) builds this clock from the boot-time offset. It maps `CLOCK_MONOTONIC_RAW` to `mach_continuous_time` and `CLOCK_UPTIME_RAW` to `mach_absolute_time`. These clock identifiers are distinct, and the adapter must not use them interchangeably as evidence about sleep. Authority access charges elapsed time from the retained timestamp, and lifetime locks keep owning physical work. A sleep interval can change elapsed charges and refill. Elapsed time can neither reclaim a live owner nor create a second authority. The physical sleep fixture must verify the actual clock behavior and the ownership behavior together. Source review and ordinary hosted CI cannot establish a real sleep/wake transition.

`tests/coordination_macos.rs` adds a dedicated subprocess that joins and then enters a sandbox that denies filesystem access. It asserts explicit unavailability before the join, fencing after the join with no local charges, and no journal mutation. A privileged root-transition subprocess checks that an existing governor and an Auto reopen both reject the incompatible root, and that a separately requested root-local authority keeps its charges. The workflow provisions tmpfs and runs these tests and the process benchmarks on both Mac architectures. Both architectures pass the native integration suite, including the root and sandbox transitions. The dedicated acceptance workflow also collects aggregate resources. Real sleep/wake remains a separate gate. The macos-26 runner rejects system sleep, and the macos-26-intel runner records no kernel sleep/wake transition. The physical test needs a sleep-capable runner named by the COORDINATION_SLEEP_RUNNER variable or the workflow dispatch input. The test runs only for default-branch pushes and manual dispatches, so pull requests and other refs cannot schedule this privileged job.

## FreeBSD

FreeBSD `flock` supports nonblocking acquisition and keeps shared lock references across `dup` and `fork`. The documentation also describes how `flock` interacts with `fcntl` and `lockf`, so the adapter must use one locking interface throughout. See [FreeBSD 15.0 `flock(2)`](https://man.freebsd.org/cgi/man.cgi?manpath=FreeBSD+15.0-RELEASE&query=flock&sektion=2).

`coordination::freebsd::Scope` uses the shared Unix tmpfs journal and pinned anchor implementation. Discovery requires an administrator-mounted tmpfs at `/var/run/tree-fucker`, and explicit directories must also be on tmpfs. Before it opens retained state, the adapter verifies the filesystem type, the effective ownership, the private permissions, and the filesystem root identity. It uses FreeBSD monotonic time for the lifetime of that tmpfs mount. Declared storage domains stay participant-private accounts under the shared aggregate envelope.

Host and jail processes with the same filesystem root and effective user may join the same authority, because they see the same retained files and the same kernel monotonic clock. Separate jail names or numeric IDs do not create separate budgets. A different filesystem root is incompatible even if it exposes the original retained directory, and Auto mode must not downgrade this mismatch to process-only governance. A jail with its own root can explicitly create an authority on its own tmpfs view.

FreeBSD reports zero for the caller's own jail ID in `kinfo_proc`, so the adapter does not use that ID as a namespace identifier. See [FreeBSD kernel process information](https://cgit.freebsd.org/src/tree/sys/kern/kern_proc.c?id=645743ea99829e6d578cca5a580cf0a4102fb7dd). The adapter rechecks the root identity and the effective user on each access. A caller in capability mode gets an explicit unavailable result before joining, and entering capability mode fences an existing handle. The default kernel policy blocks jail entry while the authority's directory descriptors are open. After those handles close, a reopen from a compatible jail keeps the same generation and the prior charges.

Native tests hold real FIFO work in one jail and deny dispatch from another jail under the same physical ceiling. They also verify rejection of an incompatible root with no journal modification, retention of a separate-root local authority, retention of charges from host to jail, and effective-user isolation. Owner descriptors are released only by closing, and inherited API handles reject use after a fork before they touch a process mutex. The shared process suite covers fork, exec, and dup lifetime, final-close retention, and interrupted updates.

## illumos and Solaris

These targets have separate lock contracts. Current illumos documents open-file-description locking through `F_OFD_SETLK` and a `flock` that is compatible with Linux and BSD. These locks survive duplicated and inherited descriptions and release on the last close. The POSIX locks of illumos belong to a process and can disappear when another descriptor for the same file closes. See [illumos `fcntl(2)`](https://smartos.org/man/2/fcntl).

`coordination::illumos::Scope` uses nonblocking native `flock`, verified tmpfs, a pinned anchor, and the shared bounded journal. Discovery requires an administrator-created sticky directory at `/var/run/tree-fucker` on tmpfs. The effective user, the root identity, the numeric zone ID, and the kernel's non-reused zone incarnation qualify the scope. The adapter reads `ZONE_ATTR_UNIQID` on each context check, so a recreated zone with a repeated numeric ID gets a new scope identity. The monotonic epoch and the tmpfs storage share a boot lifetime. Domain accounts stay participant-private under the aggregate envelope. The adapter has no POSIX-lock fallback.

The Solaris `fcntl` contract describes record locks that belong to a process, that forked children do not inherit, and that release when any descriptor for the file closes. That contract does not meet the owner-slot invariant. Before shared coordination can be enabled, Solaris needs a separately verified description-lifetime mechanism or a native process-lifetime design. See [Oracle Solaris `fcntl(2)`](https://docs.oracle.com/cd/E88353_01/html/E37841/fcntl-2.html).

`tests/coordination_socket_lifetime.rs` evaluates a bound Unix datagram endpoint as a candidate lifetime mechanism for Solaris. Repeated nonblocking connects send no messages. Duplicate and inherited descriptions keep the endpoint alive after the original owner closes or dies. A connected probe does not keep a closed owner discoverable. These histories pass on Linux, FreeBSD, and OmniOS, and OmniOS reports `EDESTADDRREQ` for the retained pathname after final close. Solaris cross-compilation passes. The dedicated acceptance workflow boots Solaris 11.4 in a VM and installs the native Rust distribution directly, because current rustup cannot lock its settings file on Solaris. No authority uses this candidate yet. A Solaris port still needs native evidence, identity and replacement fencing, and a bookkeeping lock that keeps exclusion when an unrelated descriptor closes.

Native acceptance must cover independent zones, privilege restrictions, closing an unrelated descriptor to a locked inode, duplicated and inherited ownership, writer death, owner death, final-participant exit, and generation replacement. OmniOS acceptance does not establish Solaris acceptance.

## Evidence required for a port

The support entry for an adapter records the exact OS and release, the architecture, the storage type, the security and namespace boundary, the clock, the lifetime mechanism, and the native test run. The adapter must run the shared twenty-process ceiling tests with actual held work, all lifecycle cancellation cases, interrupted publication and replay, restart and debt retention, and scope replacement histories. Its resource reports cover startup and churn, steady contention, blocked work, and idle behavior. A port is ready for release only after those results establish its contract.
